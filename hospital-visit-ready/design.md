# 정체성과 원칙

## 정체성 
- 이 앱은 병원에 가기 전 환자가 자신의 상태를 일목요연하게 정리해서 의사에게 전달 할 수 있도록 돕는 도구이자, 추후 자신의 상태를 트랙킹 할 수 있는 웹이다.
- 타겟은 건강에 관심이 많은 만성질환자 혹은 부모님을 봉양하는 자녀.
- 톤앤매너는 깔끔하고 직관적인 ui, 친절한 어투 사용
- 현재는 화면을 그리고, 추후에 백엔드 로직을 붙인다. 기본적으로는 브라우저에 저장하는 것을 원칙으로 하되, 추후 로그인 기능이 도입되면 로그인한 회원에 대해서는 DB에 저장한다.

# 최우선 원칙

1. 사용자가 미리 알아야 하는 건 없다. 어디가, 언제부터만 고르면 나머지는 에이전트가 되묻는다. 
2. 칩은 지름길이다. 자유 입력이 항상 열려 있고, 칩 세트의 마지막은 항상 탈출구 보유 ("잘 모르겠어", "없어", "기억 안 남").
3. 로그인 없이 사용할 수 있음. 로그인 없이 사용하는 유저는 local에 저장. 단 로그인 하면 프로필, 사진, 진료 메모는 전부 DB에 남긴다.
4. 날짜를 지어내지 않는다. 모르면 한 번만 되묻고 범위("이번 달 초")로 적는다.
5. 약 정보는 공공데이터(식약처 낱알식별, e약은요, DUR) 인용까지만 허용. "등록돼 있어요, 의사에게 확인하세요"에서 멈춘다.
6. 진료과는 규칙표로 1~3위. 진단이 아니다. 애매하면 내과 또는 가정의학과.
7. 사진은 모델에 보내지 않는다. 저장해서 의사에게 보여 주는 용도. PDF는 window.print().
8. 응급 신호 10개 중 하나라도 걸리면 어느 단계에서든 대본 없이 119 화면만.
9. AI agent 가 응답을 준비할때는 progress 를 나타내는 상태표시가 들어가야 한다.

# 2. 디자인 토큰

디자인 토큰은 화면에서 쓰는 색·글자·간격·모서리·그림자·모션을 역할별로 정리한 값이다. 코드에서 색이나 간격을 직접 하드코딩한 부분이 보이면 여기로 가져와서 바꾼다.

## 2.1 색

메인 색은 거의 검정에 가까운 네이비다. 넓은 면에 깔지 말고 앱바, 사용자 말풍선, 주 버튼, 본문 글자에만 쓴다. 바탕은 아주 옅은 회청색이다.

### 2.1.1 브랜드/메인 색

- `--c-primary`: `#17232B` — 앱바, 사용자 말풍선, 주 버튼, 본문 글자
- `--c-primary-hover`: `#24343F`
- `--c-primary-soft`: `#3D4F5B` — 보조 아이콘, 비활성 주 버튼
- `--c-primary-tint`: `#E9EEF1` — 선택된 칩 배경, 강조 행 배경

### 2.1.2 뉴트럴

- `--c-bg`: `#F4F6F8` — 페이지 바탕, 채팅 영역
- `--c-surface`: `#FFFFFF` — 말풍선(에이전트), 카드, 입력창
- `--c-border`: `#D9E0E5`
- `--c-border-strong`: `#B8C3CB`
- `--c-text`: `#17232B`
- `--c-text-2`: `#5B6B75` — 힌트, 캡션, 메타
- `--c-text-3`: `#8A98A2` — placeholder, 비활성

### 2.1.3 시맨틱

- `--c-danger`: `#C4342D` — 119 카드 제목, 전화 버튼
- `--c-danger-bg`: `#FBECEA`
- `--c-danger-border`: `#E8A29D`
- `--c-success`: `#2E7D5B` — "저장했어요" 같은 확인 문구에만
- `--c-photo-skin`: `#F2C6B8` — 사진 썸네일 placeholder

### 2.1.4 대비 확인

- `#17232B` on `#FFFFFF` = 14.6:1
- `#5B6B75` on `#FFFFFF` = 5.6:1
- `#FFFFFF` on `#17232B` = 14.6:1
- 모두 AA 통과

### 2.1.5 색상 사용 규칙

- 메인 네이비는 넓은 배경에 쓰지 않는다. 강조는 색 면적보다 용도(앱바, 사용자 말풍선, 주 버튼, 본문 글자)로 차별화한다.
- 배경은 옅은 회청색을 기본으로 하고, 표면은 흰색으로 올려서 읽기 영역을 분리한다.
- danger는 응급/경고 전용으로 분리한다. 일반 강조나 브랜드 강조와 섞지 않는다.
- success는 확인 문구에만 쓴다. 상태나 행동의 일반 강조로 확대하지 않는다.
- 사진 placeholder는 별도 스킨 톤으로 구분해 실제 사진 썸네일과 착각하지 않게 한다.

## 2.2 타이포

글자 체계는 읽는 용도의 본문과, 짧게 눈에 먼저 보이는 요소로 나눈다.

- `--font`: `"Pretendard Variable"`, Pretendard, `-apple-system`, `"Apple SD Gothic Neo"`, `"Noto Sans KR"`, sans-serif
- `--fs-title`: `17px` — 앱바 제목, 카드 섹션 제목 (600)
- `--fs-body`: `15px` — 말풍선, 칩, 입력 (400/500)
- `--fs-hint`: `12px` — 말풍선 아래 회색 안내, 캡션 (400)
- `--fs-h1`: `24px` — 119 화면 "지금 119" (700)
- `--lh`: `1.5`

### 2.2.1 타이포 규칙

- 한글은 12px 아래로 내리지 않는다. 힌트가 12px이고, 그 외는 15px 이상이다.
- 같은 정보 레벨은 화면마다 글자 크기를 제멋대로 바꾸지 않는다.
- 말풍선 본문은 읽기 편한 크기로 두고, 버튼·칩 라벨도 너무 작지 않게 한다.
- 정보 강조가 필요할 때는 글자 크기보다 색/굵기/레이블로 구분한다.

## 2.3 간격, 모서리, 그림자

간격은 기준 단위로 묶고, 모서리는 형태별로 고정 값을 쓴다.

- `--sp-1`: `4px`
- `--sp-2`: `8px`
- `--sp-3`: `12px`
- `--sp-4`: `16px`
- `--sp-5`: `20px`
- `--sp-6`: `24px`
- `--r-bubble`: `12px` — 말풍선, 카드
- `--r-chip`: `999px` — 칩, 프로필 버튼
- `--r-input`: `12px`
- `--r-btn`: `999px` — 주/보조 버튼
- `--shadow-card`: `0 1px 2px rgba(23,35,43,.06)` — 카드 하나. 말풍선에는 그림자 없음
- `--tap-min`: `44px` — 터치 최소 높이

### 2.3.1 간격/모서리/그림자 규칙

- 그림자는 결과 카드와 드로어에만 쓴다. 말풍선, 칩은 테두리로만 구분한다.
- 같은 모양의 요소가 여기저기 흩어져도 반지름이 제각각으로 보이지 않게 한다.
- 터치 타겟은 최소 44px를 목표로 잡는다.
- 카드처럼 필요한 요소만 살짝 띄우고, 채팅 말풍선처럼 흐름 안에 있는 요소는 과하게 띄우지 않는다.

## 2.4 모션

모션은 진입/교체/열림에만 쓰고, 응급 화면은 즉시 표시한다.

- 말풍선 등장: `opacity 0→1`, `translateY 6px→0`, `160ms ease-out`
- 칩 트레이 교체: 이전 칩 fade-out `120ms`, 새 칩 fade-in `160ms`. 동시에 하지 않는다.
- 드로어: `translateX -100%→0`, `200ms`
- 119 카드: 애니메이션 없음. 즉시.
- `prefers-reduced-motion`이면 전부 `0ms`.

### 2.4.1 모션 규칙

- 말풍선은 순차적으로 등장하는 느낌만 주고, 과하게 움직이지 않는다.
- 칩 세트가 바뀔 때는 이전 칩이 먼저 사라지고 새 칩이 들어오게 해서 급작스러운 전환을 줄인다.
- 응급 화면은 어떤 애니메이션도 넣지 않는다. 정보가 먼저 보이게 한다.
- 사용자가 모션 축소를 요청했으면 모든 전환을 끈다.

# 3. 레이아웃 프레임워크

레이아웃은 화면이 여러 개로 늘어나도 같은 틀로 굴러가게 하는 뼈대다. 지금은 챗봇 중심 단일 화면이지만, 상단바·사이드바·메인·플로팅 요소의 자리 역할을 먼저 정해 둔다. 이 절에서 정하는 건 "무엇이 어디에 붙는지"이고, 색·글자·간격은 2번 토큰이 맡는다.

## 3.1 앱셸 구조

앱 전체는 모바일 우선으로 본다. 화면 전체가 앱셸이고, 바깥 배경을 나중에 덧씌우는 방식이다.

- 셸은 세로 3분할이다. `grid-template-rows: auto 1fr auto`로, 위쪽 앱바 / 가운데 메시지 영역 / 아래쪽 입력바 순서를 고정한다.
- 셸 높이는 `100dvh`로 잡고, 화면 전체를 채운다.
- 가운데 메시지 영역은 스크롤이 필요한 곳이고, 입력바는 항상 하단에 붙는다.
- 배경은 셸 바깥을 `--c-bg`로 채우는 방식으로 처리한다. 셸 자체는 입력바·메시지 영역의 표면 색을 쓴다.

## 3.2 반응형 기준점

반응형은 세 구간으로 본다. 기준은 너비와 셸의 거동 차이다.

### 3.2.1 768px 미만

- 화면 전체가 셸이다. 별도의 바깥 배경 영역이 없고, 셸이 뷰포트를 그대로 채운다.
- 앱바는 고정 상단으로 둔다.
- 입력바는 고정 하단으로 둔다. 하단에는 `env(safe-area-inset-bottom)`을 반영한다.
- 가운데는 메시지 영역만 차지한다.
- 가로 스크롤은 금지한다. 칩은 `flex-wrap: wrap`으로 처리한다.
- 즉, 모바일에서는 앱셸이 곧 화면 레이아웃 전체다.

### 3.2.2 768px 이상

- 셸을 가로 `480px`로 고정한다.
- 셸은 가운데 정렬로 놓는다. `margin: 0 auto` 계열로 처리한다.
- 바깥(body)은 `--c-bg`로 채운다.
- 셸 양옆에 테두리를 넣는다. `border-left: 1px solid var(--c-border)`, `border-right: 1px solid var(--c-border)`.
- 세로는 `100dvh`를 유지한다.
- 앱바 고정 상단, 입력바 고정 하단 구조는 그대로 유지한다.

### 3.2.3 1024px 이상

- 기본 구조는 768px 이상과 같다.
- 셸의 가로 중심성과 480px 고정은 유지한다.
- 결과 카드(8장)만 예외적으로 더 넓게 허용한다. 결과 카드는 최대 `640px`까지 넓어질 수 있다.
- 나머지 화면 요소는 480px 셸 안에서 움직인다.

## 3.3 셸 그리드 정의

셸은 3행 그리드다.

- 첫 행: 앱바. 높이는 자동.
- 둘째 행: 메시지 영역. 남은 공간을 모두 차지한다.
- 셋째 행: 입력바/칩 트레이 영역. 높이는 자동.
- 셸 전체는 `display: grid`로 놓고, `grid-template-rows: auto 1fr auto`를 쓴다.
- 세로는 `100dvh`, 최대 너비는 `480px`, 가운데 정렬은 `margin: 0 auto`.
- 배경은 `var(--c-bg)` 계열로 처리한다.

```css
.shell {
  display: grid;
  grid-template-rows: auto 1fr auto;   /* appbar / messages / tray+input */
  height: 100dvh;
  max-width: 480px;
  margin: 0 auto;
  background: var(--c-bg);
}
```

## 3.4 반응형 보정과 테두리

768px 이상에서만 셸 바깥 처리와 테두리를 켠다.

```css
@media (min-width: 768px) {
  body { background: var(--c-bg); }
  .shell { border-left: 1px solid var(--c-border); border-right: 1px solid var(--c-border); }
}
```

이 처리는 "셸이 카드처럼 보이게" 하는 용도다. 모바일에서는 셸이 화면 전체를 차지하므로 테두리를 넣지 않는다. 1024px 이상에서도 이 처리는 그대로 유지하되, 결과 카드만 예외 폭으로 넓어진다.

## 3.5 앱바와 입력바 고정

- 앱바는 셸의 첫 행에 고정한다. 페이지가 스크롤되어도 앱바는 화면 상단에 남아 있어야 한다.
- 입력바는 셸의 마지막 행에 고정한다. 메시지 영역이 길어지더라도 하단에 붙어 있어야 한다.
- 입력바 하단에는 `env(safe-area-inset-bottom)`을 패딩으로 반영한다. 모바일에서 홈 영역과 겹치지 않게 한다.
- 앱바와 입력바 높이·내부 여백은 화면 구간마다 다른 값으로 흩어지지 않게 한다.

## 3.6 메시지 영역

- 메시지 영역은 `overflow-y: auto`로 스크롤 처리한다.
- 새 메시지가 오면 맨 아래로 스크롤된다. 매번 자연스러운 아래로 이동이 목적이다.
- 메시지 영역은 셸의 가운데 행이라서, 앱바와 입력바 사이에서만 늘어난다.
- 말풍선, 시스템 안내, 칩 트레이 등은 모두 이 영역 안에서 움직인다.
- 가로 스크롤은 허용하지 않는다. 레이아웃은 세로만 늘어난다.

## 3.7 칩 트레이 위치

- 칩 트레이는 메시지 영역 맨 아래, 입력바 바로 위에 붙는다.
- 칩 트레이는 스크롤 영역 밖에 따로 두지 않는다. 메시지 영역 안이다.
- 칩 세트가 바뀌면 메시지 영역 안에서 위아래 배치만 조정된다.
- 칩이 여러 줄일 때는 `flex-wrap: wrap`으로 처리하고, 가로로 삐져나가지 않게 한다.
- 칩과 입력바는 같은 하단 블록을 공유할 수 있지만, 칩은 메시지 영역의 일부로 본다.

## 3.8 가로 스크롤 금지

- 어떤 화면·어떤 컴포넌트에서도 가로 방향으로 콘텐츠가 삐져나와 스크롤이 생기지 않게 한다.
- 칩은 무조건 `flex-wrap: wrap`으로 처리한다.
- 버튼·말풍선·카드 같은 요소는 최대 폭 규칙을 지켜서 옆으로 넘어가지 않게 한다.
- 반응형 구간에서 너비가 바뀔 때도 가로 넘침이 생기지 않아야 한다.

## 3.9 레이아웃 원칙

- 모바일 우선으로 잡고, 넓은 화면에서는 셸을 가운데로 좁혀서 본다.
- 셸은 세 구간에서만 달라지고, 내부 원리(앱바/메시지/입력바)는 같다.
- 768px 이상부터는 셸 바깥에 배경을 넣고 테두리로 셸을 분리한다.
- 1024px 이상에서는 셸은 그대로 두고, 결과 카드만 예외 폭을 준다.
- 메시지 영역은 스크롤 영역이고, 칩 트레이는 그 안 맨 아래에 붙는다.
- 입력바 하단에는 safe-area를 반영한다.
- 가로 스크롤은 어떤 경우에도 만들지 않는다.
- 레이아웃이 바뀌더라도 토큰, 컴포넌트 규격, 카피와 섞이지 않게 한다. 레이아웃은 자리만 맡는다.

# 4. 컴포넌트 규격

- **Danger**: 배경 `--c-danger`, 흰 글자. 예: "119 전화하기" (`href="tel:119"`).

# 5. 단계 설정

앱 전체는 사용자의 응답을 받아서 다음 단계로 넘어가는 흐름으로 본다. 지금은 화면에서 "몇 번 화면"이라고 부르는 단계들이 이미 여러 개 언급되고 있으므로, 그 맥락을 그대로 단계 순서로 정리한다.

## 5.1 단계 흐름

단계 흐름은 아래와 같이 본다.

1. **시작/초기 질문**: 어디가 아픈지 묻는 단계. 너무 많은 사전 지식을 요구하지 않는다.
2. **부위 선택 / 증상 선택**: 버튼(칩)으로 고르거나, 글로 답할 수 있다.
3. **증상 설명**: 어떻게 아픈지, 언제부터인지 등을 정리한다.
4. **약/진료과 관련 정보 정리**: 필요하면 약 이름, 진료과 추천 같은 정보를 정리한다.
5. **결과 카드 / 요약 화면**: 지금까지 모은 내용을 카드 형태로 묶어 보여준다.
6. **응급 화면**: 응급 신호가 걸리면 어느 단계든 이 화면으로 넘어간다.
7. **기록/진료 준비 관련 화면**: 진료 기록, 프로필, 지난 진료 등을 다루는 화면.
8. **기록 삭제 확인 등 확인 단계**: 삭제나 민감 동작 전에 확인을 받는 단계.

지금 단계에서는 번호를 "화면을 가리키는 식별자"로도 같이 쓰고 있으므로, 아래 6장에서 화면별로 다시 묶는다.

## 5.2 단계 간 전환 규칙

- 단계 전환은 사용자가 무엇을 선택했는지/입력했는지에 따라 일어난다.
- 칩으로 고르는 방법도 있고, 글로 직접 입력하는 방법도 항상 열려 있어야 한다.
- 단계마다 입력 방식이 조금씩 달라질 수 있지만, "뭐라도 답할 수 있다"는 방향은 유지한다.
- 단계가 바뀔 때 칩 세트가 바뀌면, 이전 칩은 먼저 사라지고 새 칩이 들어온다. 동시에 교체하지 않는다.

## 5.3 단계 상태 규칙

- 각 단계는 "아직 시작 안 함 / 진행 중 / 완료" 같은 상태로 볼 수 있다.
- 단계 상태는 화면에 따라 다르게 보일 수 있지만, 한 앱 안에서는 같은 방식으로 다루는 게 좋다.
- 나중에 백엔드를 붙여도 단계 상태 개념 자체는 유지하고, 저장 위치만 바꾸도록 한다.

## 5.4 단계 설계 원칙

- 사용자에게 처음부터 많은 정보를 요구하지 않는다. 처음에는 어디가 아픈지, 언제부터인지처럼 적은 정보부터 받는다.
- 칩은 빠른 선택지이고, 마지막 칩은 항상 탈출구를 가진다. "잘 모르겠어", "없어", "기억 안 남" 같은 선택지가 필요하다.
- 날짜나 약 정보처럼 불확실한 내용은 지어내지 않는다. 필요하면 한 번 더 묻고, 모를 때는 범위 표현으로 남긴다.
- 응급 신호가 잡히면 단계 흐름과 상관없이 응급 화면으로 넘어간다.

# 6. 화면 명세

화면은 메인 화면 한 개에서 대화형으로 이루어진다. 지금의 화면 명세는 예시일 뿐이며, 단계는 건너뛸 수 있다. 이 단계는 추후 agent API나 skill 호출을 통해 화면이 나오는 순서가 달라질 수 있다.

백엔드 혹은 agent-api/skill을 붙이기 전에는 한군데에서 관리한 agent의 말로 AgentBubble을 구성하고, 이외에는 agent의 응답 혹은 백엔드의 응답을 API로 가져온다.

## S1 첫 화면

셸 + where 단계. 로그인, 온보딩, 설명 화면 없음. 열자마자 질문.

칩 8개가 입력바 위에 2줄로. 스크롤 없이 한 화면.

"여러 군데"를 누르면: UserBubble "여러 군데" → AgentBubble "어디부터요? 하나씩 골라요" → 같은 칩 트레이(여러 군데 제외). 고르면 "또 있어요?" → "다음 부위 / 이제 없어". 최대 3곳. 이후 단계는 첫 번째 부위 기준으로 진행하고, 결과 카드에 나머지 부위를 한 줄로 붙인다.

자유 입력이 들어오면 부위 키워드를 매칭(머리, 두통 → 머리 등). 매칭 실패 시 "여러 군데" 취급하지 않고 "어디 근처예요?"로 한 번 되 묻고, 그래도 없으면 부위를 "기타"로 두고 진행.

## S2 사진 찍어 두기

where ∈ {피부, 눈}일 때만 진입. 그 외 부위는 S3로 바로.

"사진 찍기" → `<input type="file" accept="image/*" capture="environment">`. 찍으면 PhotoBubble(썸네일 + "M/D 밤|아침", 18시 이후면 밤) → AgentBubble "저장했어요. 이 브라우저에만 남고 서버로는 안 가요." → 칩 "사진 더 찍기 / 다음".

사진은 IndexedDB에 Blob으로. 모델, 서버에 절대 보내지 않는다.

카메라 버튼(InputBar)은 어느 단계에서든 같은 동작. 찍으면 현재 단계는 그대로 두고 PhotoBubble만 추가.

## S3 어떻게 아파

how 단계. 질문에 부위 이름이 들어간다("피부가 어떻게 아파요?").

칩은 부위별 표. 마지막은 "설명하기 어려워" → 자유 입력을 유도하는 AgentBubble "한 단어로도 돼요. 예: 화끈, 욱신".

통증 계열이면 worse로, 아니면 since로.

## S4 언제부터

since 단계. 칩 마지막 "기억 안 남".

자유 입력에 "몰라, 모르겠" 류가 오면 since-retry 1회. 그 답도 모르면 값은 "기억 안 남". 절대 날짜를 만들지 않는다. 저장 값은 칩 문자열 그대로(예: "2주 넘게"), ISO 날짜 아님.

## S5 먹는 약

meds 단계. "최근 처방약 불러오기" 칩은 이 브라우저에 지난 진료 메모(S8 진료 후 메모)가 1건 이상 있을 때만 렌더.

"약 이름 입력" → 자유 입력. e약은요 API로 이름 조회, 결과는 "등록돼 있어요" 한 줄과 제조사만. 효능, 복용법은 쓰지 않는다.

"이름은 모르고 하얀 알약" 같은 자유 입력이 오면 → AgentBubble "그럼 모양이랑 색으로 찾아볼게요." → S6.

"안 먹어" → S7.

## S6 모양이랑 색으로 찾기 (풀스크린 패널)

채팅 셸 위에 덮는 패널. AppBar 우측 버튼이 "닫기". InputBar에 카메라 없음, placeholder "약 이름을 알면 여기에".

섹션: (1) 모양 6개 아이콘 버튼(원형, 타원, 장방형, 삼각, 사각, ? 기타) 단일 선택. (2) 색 8개 원형 스와치(하양, 노랑, 주황, 분홍, 빨강, 파랑, 초록, 보라) 단일 선택. (3) 새겨진 글자 텍스트 필드 "없으면 비워 둬요".

모양 또는 색 하나라도 고르면 식약처 낱알식별 API 호출(텍스트 파라미터만, 비전 없음). 후보는 최대 5개, "후보 N개" 제목 아래 카드 리스트: 이름 15/600, 제조사 · 모양 · 색 · 각인 12. 우측 "이 약" 버튼(선택하면 Primary).

하단 안내 12px: "고른 약은 e약은요, 그다음 DUR(같은 계열 겹침, 같이 먹으면 안 되는 조합, 65세 이상 주의) 순서로 확인해요. 결과는 '등록돼 있어요, 의사에게 확인하세요'까지만 말해요."

후보 0개: "이 조합으로는 못 찾았어요. 약 봉투나 처방전 사진을 찍어 두면 의사에게 보여 줄 수 있어요." + 칩 "사진 찍기 / 그냥 넘어가기".

API 실패: 같은 문구 + "지금 조회가 안 돼요". 절대 추측 결과를 내지 않는다.

"이 약" 선택 → 패널 닫힘 → UserBubble "타이레놀정500mg" → S7.

## S7 해 본 거 + 질문 3개

tried 단계. "병원 다녀왔어" → tried-visit 자유 입력 → 값은 지난 진료 이력에 저장.

이어서 questions: 에이전트가 답한 내용으로 질문 3개를 먼저 만들어 AgentBubble에 번호 목록으로 보여 준다. 사용자는 고르기만.

"이대로" → S8
"하나 바꿀래" → 칩 "1번 / 2번 / 3번" → 자유 입력으로 교체
"직접 추가" → 자유 입력 → 4번째로 추가(최대 4)

질문 생성 규칙(모델 없이 규칙표): 약을 골랐으면 "이 약 계속 먹어도 되나요", worse가 있으면 "{worse}에 더 심해지는 건 왜 그런가요", tried가 있으면 "{tried}했는데 그대로면 다른 원인일 수 있나요", 항상 마지막 후보 "검사가 필요한가요".

## S8 결과 카드

채팅 영역 전체가 Card 하나. InputBar 없음(진료 후 메모 필드가 대신).

섹션 순서 고정:

1. **어느 과로 갈까요** — 1~3위. 번호 원(1위만 `--c-primary` 채움, 2·3위는 테두리) + 과 이름 15/600 + 근거 한 줄 12. 아래 12px "규칙표로 고른 거예요. 진단이 아니에요."
2. **진료실에서 이렇게 말해요** — 1인칭 대본 4~6문장. 순서: 부위+양상 → 시작 시점(범위) → 악화 조건 → 해 본 것/지난 진료 → 먹는 약. 날짜는 사용자가 고른 문자열 그대로.
3. **꼭 물어볼 세 가지** — 번호 목록.
4. **찍어 둔 사진** — 가로 나열 96×96 + 캡션. 없으면 섹션 생략.
5. 버튼 2개 가로: Primary "복사"(대본+질문을 plain text로 clipboard), Secondary "PDF로 저장"(`window.print()`, print CSS는 카드만).
6. **진료 후 메모** — textarea placeholder "의사가 뭐라고 했는지 적어 두면 다음 대본에 들어가요". blur 시 자동 저장.

진료과 규칙표(v1 최소): 피부 → 피부과, 가정의학과, (긁으면 심해지고 반복) 알레르기내과 / 배 → 내과, 가정의학과 / 머리 → 신경과, 내과 / 허리·관절 → 정형외과, 재활의학과 / 귀·코·목 → 이비인후과, 내과 / 눈 → 안과 / 가슴 → 119 감지 우선, 아니면 내과, 가정의학과.

## S9 응급 신호

어느 단계에서든 자유 입력 또는 칩 조합이 아래 10개 중 하나에 걸리면 즉시. 애니메이션 없음. InputBar 전체 비활성. 칩 없음. 대본 안 만든다.

카드(Danger 변형): 제목 "지금 119" 24/700 `--c-danger`, 본문 "{걸린 신호}이 {조건} 계속되는 건 바로 병원에 가야 하는 신호예요. 대본은 만들지 않아요.", Danger 버튼 "119 전화하기" `tel:119`.

카드 아래 12px: "응급 신호 10개 중 하나라도 걸리면 이 화면만 나와요." + 목록.

신호 10개: 의식 저하 / 한쪽 마비 / 흉통 20분 이상 / 호흡곤란 / 지혈 안 됨 / 급성 두통 / 경련 / 토혈 / 딱딱한 복통 / 고열+목 뻣뻣함.

판정은 키워드 표(모델 없이): 예) 흉통 = (가슴 ∧ (쥐어짜|조여|눌리)) ∧ (20분|30분|계속). 부위 "가슴" + how 통증 + since 오늘이면 worse 대신 "지금 몇 분째예요?"를 먼저 묻는다.

되돌아가기 없음. 새로 시작하려면 드로어 "+ 새 진료 준비".

## S10 진료 기록 (드로어)

햄버거 → Drawer. 제목 "진료 기록", 캡션 "이 브라우저에만 저장, 암호화".

프로필: 리스트. 선택 항목은 Primary 채움. "나 (34)", "어머니 (68)". 맨 아래 "+ 프로필 추가"(이름, 나이만. 나이는 65세 이상 DUR 주의에 쓴다).

지난 진료: 최신순. 행 = 날짜(M/D) + 제목("피부, 팔 안쪽") + 요약 12("대본 만듦, 사진 2장" / "접촉성 피부염, 연고 처방"). 탭하면 그 결과 카드(S8)를 읽기 전용으로 연다.

"+ 새 진료 준비" → 드로어 닫고 S1. 진행 중 대화가 있으면 "지금 것 버리고 새로 시작할까요?" 확인.

"기록 전부 지우기" → 확인 시트 "이 브라우저의 프로필, 사진, 메모를 전부 지워요. 되돌릴 수 없어요." Danger "지우기" / Secondary "취소".

# 7. 데이터 구조

지금은 브라우저 저장 중심이고, 나중에 백엔드를 붙일 수 있게 구조를 잡는다. UI 컴포넌트와 저장 형식을 직접 붙이지 말고, 앱 상태 객체와 저장/불러오기 책임을 분리한다.

## 7.1 저장 대상

지금 브라우저에 저장할 후보:

- 현재 단계/화면 상태
- 사용자가 선택한 부위, 증상, 시기 관련 정보
- 텍스트 답변, 첨부한 사진 정보
- 약/진료과 관련 정리 결과
- 프로필, 지난 진료, 진료 메모 같은 기록 정보
- 로그인 전에는 로컬 저장, 로그인 후에는 프로필·사진·진료 메모를 DB 저장 대상으로 전환할 수 있어야 한다.

## 7.2 데이터 구조 원칙

- 화면마다 제각각으로 키를 늘리지 말고, 단계/엔티티 단위로 묶는다.
- 예: 방문 준비 한 건을 "진료 준비 방문" 단위로 보고, 그 안에 부위·증상·사진·약·진료과·요약 같은 하위 항목을 둔다.
- 텍스트와 사진 파일은 구분한다. 사진은 모델에 보내지 않으므로, 저장/표시/전달 관점에서 따로 다룬다.
- 날짜는 지어내지 않는다. 모르면 한 번만 되묻고, 범위를 쓸 수 있으면 범위 표현으로 남긴다.
- 약 정보는 공공데이터 인용 정보 정도로만 남긴다. 앱이 약에 대해 단정하는 내용은 저장하지 않는다.

## 7.3 권장 상태 객체 뼈대

아래처럼 생각하면 나중에 백엔드로 옮기기 쉽다.

- `visit`: 한 번의 진료 준비 단위
  - `id`
  - `createdAt`, `updatedAt`
  - `status`: 예: 시작 전/진행 중/정리 완료/응급 등
  - `symptoms`: 부위, 증상 설명, 시기 표현 등
  - `photos`: 사진 메타데이터 목록(실제 파일은 별도 저장소/로컬 파일 참조)
  - `medications`: 약 관련 참고 정보
  - `departmentSuggestions`: 진료과 추천 결과
  - `summary`: 결과 요약에 쓸 텍스트
  - `emergency`: 응급 신호 판단 결과
- `profile`: 사용자 프로필이 생기면 분리
- `history`: 지난 진료/진료 준비 기록

지금은 이 구조를 그대로 모두 구현하라는 뜻이 아니라, 앞으로 저장/유지보수를 쉽게 하기 위한 방향 설명이다.

## 7.4 저장/불러오기 분리 원칙

- 상태를 화면 컴포넌트가 직접 localStorage에 쓰거나 읽지 않게 한다.
- 저장/불러오기 함수를 한 곳(예: 저장소 모듈)으로 분리한다.
- 지금은 localStorage 기반, 나중에는 같은 인터페이스를 백엔드 호출로 바꿀 수 있게 둔다.
- 로그인 여부에 따라 저장 위치를 바꾸더라도, 앱이 쓰는 데이터 형태는 최대한 유지한다.

## 7.5 로그인/백엔드 전환 시 건드릴 지점

- 로그인 전에는 프로필·사진·진료 메모를 로컬 중심으로 다룬다.
- 로그인이 붙으면 같은 정보를 DB 저장으로 전환할 수 있어야 한다.
- 전환 시 건드려야 하는 것: 저장 함수, 인증 상태, 프로필/기록 로드 방식.
- 전환 시 가능하면 건드리지 말아야 하는 것: 화면 표시 방식, 컴포넌트리, 카피, 토큰. 데이터와 표시를 섞어 두지 않는다.

# 9. 접근성, 반응형 체크리스트

## 9.1 디자인 전에 9번 체크리스트를 모두 통과했는지 확인 후 디자인한다.
- 모든 칩, 버튼 44px 이상 터치 영역 (칩은 36 높이 + 상하 4px 마진으로 44 확보)
- 칩은 <button>, 트레이는 role="group" aria-label="답 고르기"
- AgentBubble은 aria-live="polite" 영역에 추가
- 119 카드는 role="alert"
- 색만으로 상태를 구분하지 않는다 (선택 칩은 배경 + 체크 아이콘)
- 375px 폭에서 칩 8개가 2줄, 480px에서 2줄 이하
- 키보드 올라와도 입력바가 가려지지 않는다 (100dvh, visualViewport 리스너)
- @media print 에서 AppBar, InputBar, 드로어 숨김. 카드만 A4 한 장
- 다크 모드는 v1 미지원. color-scheme: light 고정
- 한글은 12px 아래로 내려가지 않는다
- 말풍선 등장, 칩 교체, 드로어 열림은 정의된 모션으로만 사용한다.
- 응급 화면은 애니메이션 없이 즉시 표시한다.
- 진행상태, 선택상태, 비활성 상태, 오류 상태가 각각 구분되게 보인다.
- AI agent 응답이 진행중일 때는 progess 되고 있는 멘트가 항상 나온다.
