# 병원 진료 대본 서비스 — PRD (ver03, agent redesign)

### 1) 한 줄 정의
증상 있는 사람(처음 아픈 본인, 또는 부모님 대신 정리해주는 자녀)이 채팅으로 말하면, **agent가 목표를 이해해 필요한 정보만 최소한으로 묻고**, 진료과 추천 1~3위 + 그대로 읽을 대본 + 질문 3개 + 사진 타임라인 + 진료 후 메모 이월을 만든다. 고정 6단계 순서로 묻는 게 아니라, **목표(진료 전 대본·질문 3개·진료과 1~3위)를 위해 필요한 단계만 필요한 만큼** 진행한다. 진단·처방이 아니라 증상 정리 + 질문 준비 도구다.

### 2) 타깃 사용자
- **주 사용자**: 증상이 있는데 어느 과인지, 뭐라고 말할지 모르는 사람. 예시: 30대 직장인이 손 오돌토돌+열 3일째인데 피부과인지 내과인지 몰라 검색만 하다가 못 가는 상황.
- **부 사용자**: 부모님 진료 기록을 대신 정리해주는 자녀(프로필 기능으로 여러 명 관리).
- **프로필 입력**: 호칭, 나이(65세 기준 노인주의 판단용), 알레르기, 만성질환까지 미리 받되, 처음 진입 시 최소한(호칭+나이)만 묻고 나머지는 "나중에 채움" 허용. 약 이름은 프로필이 아니라 대화 중 필요한 시점에 받는다.
- **사용자 입력 특징**: 첫 발화에 이미 여러 정보가 섞여 있을 수 있다(예: "3일 전부터 배가 쓰려, 타이레놀 먹었어"). Ver03에서는 이걸 6단계 순서로 다시 묻지 않고, agent가 빠뜨린 것만 골라서 묻는다.

### 3) 문제
1. 아프면 어느 과에 가야 하는지부터 모름(내과인지 소화기내과인지, 피부과인지 내과인지).
2. 진료실에 들어가면 증상을 어떤 순서로 말해야 할지 몰라서 두서없이 말하고, 의사가 묻는 것만 답하고 나옴.
3. 물어보려던 걸 못 물어보고 "네" 하고 나옴.
4. 다음 진료 때 지난번에 무슨 약을 먹었는지, 뭐라고 진단받았는지 기억이 안 나서 처음부터 다시 설명.
5. 기존 서비스는 약 이름·진료과처럼 이미 병원에 다녀온 사람만 아는 걸 미리 입력하라고 해서 처음 아픈 사람은 못 씀.
6. (Ver03 추가) 지금 구조는 6단계 순서가 코드에 고정돼 있어서, 사용자가 첫 마디에 여러 정보를 줘도 다시 묻고, 필요한 정보만 묻지 못하는 문제가 있다.

### 4) 트리거
- 사용자가 **직접 URL로 접속**. 알림 없음.
- 대표 순간:
  1. 매일 야근으로 병원 못 가다가 증상 며칠 이어져 "이제 가야겠다" 싶은 날 막막한 순간
  2. 병원 대기실에서 순서 기다리며 의사에게 조리있게 말할 내용 정리하는 순간
  3. 피부처럼 눈에 보이는 증상이 밤·아침 다르게 보여 그때그때 찍어 둬야겠다 싶은 순간
  4. 진료 끝나고 나와서 의사가 뭐라 했는지 잊기 전에 적는 순간(다음 진료에 참고)

### 5) 핵심 기능

**P0 (4개)**

| # | 기능 | 비고 |
|---|------|------|
| P0-1 | 채팅 입력 + 추천 칩 5~7개, 마지막 칩 "잘 모르겠어" | 한 번에 하나씩 묻되, agent가 필요한 질문만 추려서 함. 이미 있는 정보는 재질문하지 않음 |
| P0-2 | agent 실행부: 목표 기반 agent loop + 허용 툴 registry(6개) + 상태 JSON(5칸) + 검수 1회 + 실패 처리 + 자율성 범위 | 목표는 "진료 전 대본 + 질문 3개 + 진료과 1~3위"이고, 필요한 단계만 필요한 만큼 묻고 정보 수집. 6단계 순서는 고정이 아니라 agent가 상황에 따라 선택. 첫 발화에 정보가 많으면 다시 묻지 않음. 상태 JSON 칸 5개(부위, 증상, When(언제부터 아팠는지), 복용 중 약, 시도해본 것)를 매 턴 모델이 채우고, 채워진 칸을 빼고 빈 칸 하나를 골라 묻는다. 예: "3일 전부터 배가 쓰리고 타이레놀 먹었어"면 부위·증상·When·복용 중 약 4칸이 차므로 다음엔 시도해본 것을 묻는다. 상태 JSON은 사용자에게는 안 보이고, agent 내부에서만 저장·갱신하며 종료 시점을 판단하는 데 쓴다. 툴 6종: 1) 약 이름 확정(e약은요), 2) 효능군 중복(DUR), 3) 병용금기(DUR), 4) 노인주의(DUR), 5) 낱알식별(식약처, 텍스트 파라미터), 6) 진료과 규칙표. 툴 선택은 Upstage function calling 우선, 안 되면 JSON으로 다음 툴 이름을 주는 라우터 형태. 119/응급 신호는 매 턴 가장 먼저 검사하며 툴이 아니고 사용자 승인 없이 즉시 중단. 툴 호출 세션당 최대 8회, 초과 시 "더 확인하면 오히려 혼선이 커질 수 있어 현재 정보로 결과를 낸다"로 처리. human 승인 지점은 2개(질문 3개 확정 칩, 저장 전 동의 화면). |
| P0-3 | 출력방식: 진료과 1~3위(규칙표, 애매하면 내과·가정의학과) + 대본 카드 + 질문 3개 + 사진 날짜순 배치 + 복사 버튼 + PDF 저장 버튼(브라우저 인쇄로) | 응급이면 대본 대신 119/즉시 병원 권장만 |
|| P0-4 | 기록: 진료 후 메모 입력 → 다음 대본(이전 진료/했던 것)에 자동 반영, 처방약 입력 연계 | 비회원 localStorage, 회원 Supabase 암호화 |

**P1**

- 왼쪽 사이드 진료 기록 열람(회원은 Supabase에서, 비회원은 localStorage에서) + 사진 타임라인

### 6) 스킬·에이전트 매핑

**agent 구조 개요**
- Ver03에서 대본 생성은 Solar 단독 1회 호출이 아니라, **agent loop**로 처리한다.
- agent가 (1) 사용자 발화 이해 → (2) 필요한 정보 판단 → (3) 부족한 정보 요청 또는 도구 호출 → (4) 결과 평가 → (5) 목표 달성 시 대본·질문 3개·진료과 추천 출력 순으로 진행한다.

**agent가 사용하는 툴(tool) — 6개 (확정)**

| # | 툴 | 용도 | 선택 기준(agent 판단) |
|---|------|------|--------------------------|
| 1) | 약 이름 확정(e약은요) | 약 이름이 주어졌을 때 제품명 수준 확인·확정 | 약 이름(브랜드/제품명 level)이 있고, 약 정보를 정확히 할 필요가 있을 때 |
| 2) | 효능군 중복(DUR) | 복용 약끼리 같은 효능군인지 확인 | 복용 약이 확정됐고, 같은 계열 약 중복 점검이 의미 있을 때 |
| 3) | 병용금기(DUR) | 복용 약끼리 병용금기인지 확인 | 복용 약이 확정됐고, 약 간 병용 점검이 의미 있을 때 |
| 4) | 노인주의(DUR) | 65세 이상일 때 복용 약 노인주의 조회 | 나이 정보가 있고 65세 이상일 때 |
| 5) | 낱알식별(식약처, 텍스트 파라미터) | 약 이름을 모를 때 모양·색·각인으로 후보 제시 | 사용자가 약 이름을 모르고 모양·색·각인을 묘사할 때 |
| 6) | 진료과 규칙표 | 부위·증상 정보로 진료과 1~3위 산출 | 부위·증상 정보가 있고 진료과 추천이 필요할 때 |

- 과거 병력 조회는 Supabase 조회(회원) / localStorage(비회원)로 처리한다. 이는 P0-2 상태 JSON 밖의 과거 기록 참조용이며, 툴 6종 표에는 넣지 않는다.
- 사진 처리는 프론트↔백그라운드 연결 영역이므로 툴 표에서 제외한다.
- agent가 툴을 고르는 방식은 Upstage function calling을 우선 쓰고, function calling이 안 될 경우 JSON으로 다음 툴 이름을 주는 라우터 형태로 대체한다.
- **119/응급 신호는 별도 툴이 아니다.** 매 턴 가장 먼저 검사하고, 걸리면 툴 호출 없이 즉시 중단한다. 사용자가 따로 승인할 필요가 없다.

**if문식 분기 대신 agent 선택**
- "약 이름 있으면 e약은요"처럼 코드에서 미리 분기치는 게 아니라, agent가 현재 상태 JSON을 보고 위 6개 툴 중에서 필요한 것을 고른다.
- 단, agent가 무한정 고르는 게 아니라 허용 툴 목록(6개)·세션당 최대 8회 안에서 고른다. 8회를 넘기면 더 확인하기보다 현재 정보로 결과를 낸다.

**스킬 변경내역(PRD 스킬 매핑에 기재해야 할 것):**
- 기존 Ver02까지: Solar 1회 호출로 6항목 대본+질문 3개 생성, /api가 약 API를 조건부 분기 호출.
- Ver03에서 수정·확장:
  1) 고정 6단계 순서 제거 → 목표 기반 agent 진행으로 변경. 첫 발화에 정보가 많으면 재질문하지 않고 빠진 것만 묻는다.
  2) 도구 선택을 agent 판단으로 전환: 약 e약은요·DUR·낱알식별·진료과 규칙표·기록 조회·사진 처리를 agent가 상황에 맞게 선택(허용 도구·횟수 제한 내에서).
  3) 메모리/context 명시: 프로필(나이·알레르기·만성질환), 진료 후 메모 이월, 사진 타임라인을 agent context로 다룬다.
  4) 실패 처리 전환: "API 실패해도 대본 나온다"가 아니라, agent가 실패를 판단하고 fallback 정책에 따라 처리. 대본 중단 조건과 계속 조건을 나눈다.
  5) 자율성 범위 추가: 허용 도구 목록, tool call 상한, 접근 권한, human 승인 대상 정의.

### 7) 입력·출력

**입력(처음 온 사람 화면)**
- 채팅 화면. 에이전트가 한 번에 하나씩 묻되, 필요한 질문만 추려서 한다. 입력창 위에 추천 칩 5~7개. 칩 누르면 그 말이 대화 입력으로 들어감. 칩 없으면 타이핑. 마지막 칩은 항상 "잘 모르겠어".
- 왼쪽 위 로고 밑 펼치기 아이콘 → 진료 기록 왼쪽 사이드 열림(사진 타임라인 포함).

**입력 방식의 agent 반영**
- 사용자가 첫 발화에 여러 정보를 줄 수 있다(예: "3일 전부터 배가 쓰려, 타이레놀 먹었어").
- agent는 이걸 6단계 순서로 다시 묻지 않고, 목표 달성에 필요한 정보 중 빠진 것만 골라 묻는다.
- 추천 칩은 여전히 쓰되, chip 내용은 agent가 현재 정보 상태에 따라 적절히 제시할 수 있다.

**매 턴 진행 표시(작은 글씨)**
- 대화가 진행될 때마다 화면에 작은 글씨로 agent가 현재 무엇을 하고 있는지 표시한다.
- 표시 내용(예시): 현재 목표 + 현재 상태 요약 + 다음 계획.
  - 예: "현재 목표: 진료 전 대본 + 질문 3개 + 진료과 1~3위 정리 / 현재: 부위·증상·언제부터·복용 중 약까지 확인 / 다음: 해 본 것 확인 예정"
- 내부 상태 JSON 5칸을 그대로 노출하지 않고, 채워진 칸과 다음에 확인할 칸만 요약해 보여준다.
- 목표는 매 턴 거의 같으므로, 실제 갱신은 상태가 바뀔 때(새 칸이 채워질 때)만 일어난다.

**6단계에서 agent 진행으로 바뀌어도 유지되는 정보 요소**
- 어디가 아파(부위)
- 어떻게 아파(증상 양상)
- 언제부터(시점, 날짜 범위 허용, 모르면 대략 한 번 되묻고 안 되면 "기억 안 남", 날짜 추정·만들어내지 않음)
- 먹는 약(이름, 낱알식별 후보, 안 먹어 가능)
- 낫게 하려고 해 본 것(진료 후 메모 포함)
- 질문 3개(agent가 먼저 제안하고 칩으로 이대로/하나 바꿀래/직접 추가)

**출력**
- 응급 신호 걸림: 어느 단계에서든 119 혹은 즉시 병원 방문 권장만 출력, 대본 중단.
- 정상 출력: 대본 카드 형태
  - 진료과 1~3위(규칙표, 애매하면 내과·가정의학과)
  - 그대로 읽을 대본(6항목 순서 느낌의 읽기 문장)
  - 질문 3개
  - 찍어 둔 사진 날짜순 배치(옆에, 사진 타임라인)
  - 복사 버튼, PDF 저장 버튼(브라우저 인쇄로)
- 카드 아래: 진료 후 메모 입력. 적으면 다음 대본(이전 진료/했던 것)에 자동 반영.

**사진 처리**
- 업로드 전 브라우저에서 크기 줄이기 + 썸네일 생성 → 둘 다 암호화 → Supabase 저장(회원) 또는 localStorage(비회원).
- 읽기 시 supabase-js로 목록 받아오고 기기 키로 복호화 → img 표시.

| `DATA_API_KEY` | 공공데이터포털 인증키(e약은요·DUR·낱알식별 통합 1개) | 공공데이터포털 |
| `SUPABASE_URL` | Supabase 프로젝트 연결 주소 | Supabase 대시보드 |
| `SUPABASE_ANON_KEY` | /api에서 Supabase 클라이언트 인증용(RLS 적용) | Supabase 대시보드 |

- 위 4개는 Vercel 환경변수, /api에서만 읽음. 클라이언트 소스·응답 JSON에 값 0.
- anon 키는 브라우저에 안 감(프론트가 Supabase SDK 직접 안 씀). /api가 중계.

**표 C — 사용자 프로필 (웹 화면 입력 → localStorage 저장, 재방문 시 묻지 않음, 초기화 버튼 제공)**

| 필드 | 필수/선택 | 용도 |
|------|-----------|------|
| 호칭(아버지/어머니 등) | 선택 | 프로필 카드 표시 |
| 나이 | 선택 | 65세 이상 시 노인주의 조회 판단용 |
| 알레르기 | 선택 | 대본 생성 시 있으면 반영, 없으면 "확인 후 적기로 남김" |
| 만성질환 | 선택 | 위와 동일 |

- 처음 진입 시 호칭+나이만 묻고, 알레르기·만성질환은 "나중에 채움" 허용.
- 약 이름은 프로필이 아님. 대화 중 필요한 시점에 받는다.

**기기별 비밀(서버 못 읽음, 브라우저에만):**
- 브라우저 Web Crypto로 생성한 대칭키(AES-GCM 권장). 기기에만 둠.
- 암호화 대상: 대본, 답, 진료 후 메모, 사진 바이너리.
- 평문 필드: 날짜 라벨, 부위 라벨만 Supabase에 둠(기록 목록·타임라인 조회용).

### 9) 데이터 규칙
- 출처·기준 시각 표기: 공공데이터 출처(식품의약품안전처, 공공데이터포털) 표기. 기준 시각은 가능하면 표기(없으면 '확인 불가').
- 없는 값은 '확인 불가', 추정 금지.
- 키·프록시 주소는 서버(/api)에만. 클라이언트 소스·응답 JSON에 키 0.
- 최소 권한: Supabase RLS(user_id 기준 자기 기록만 읽고 씀). non-member는 Supabase 안 탐.
- 개인정보: 비회원 localStorage-only. 회원도 서버 평문 못 읽게(기기 암호화).
- 진료 후 메모·처방약·대본은 암호화 payload로 Supabase 저장. 평문으로 날짜·부위만 둠.
- 사진: 업로드 전 리사이즈+썸네일 생성 후 암호화. 읽을 때 프론트 복호화.
- agent 실패 기록: tool 실패·예외는 기록하되, 대본은 가능하면 진행하고, 실패한 항목은 대본에 별도 표시한다. 단, 응급 신호는 실패와 무관하게 우선 처리한다.

### 10) 성공 기준 (데모 시나리오 검증 가능 조건)

**시드 시나리오 (회원·비회원 둘 다 확인)**

**비회원(시크릿 창 테스트 포함)**  
1. 시크릿 창에서 URL로 처음 접속 → 로그인 없이 진료 시작 가능.  
2. 첫 발화에 정보가 섞여 있어도(예: "3일 전부터 배가 쓰려, 타이레놀 먹었어"), agent가 이미 있는 정보를 다시 묻지 않고 필요한 것만 묻는다.  
3. 6단계 고정 순서 진행이 아니라 필요한 단계만 거쳐 대본 카드 출력.  
4. 출력에 진료과 1~3위 + 대본 + 질문 3개 + 복사 버튼 + PDF 저장 버튼 존재.  
5. 진료 후 메모 입력 → 다음 대본(이전 진료/했던 것)에 자동 반영(로컬 재방문).  
6. 브라우저 저장값 삭제 후에도 재시작 시 안내가 스스로 나오고 최소 기능 동작.

**회원**  
1. Supabase Auth로 로그인 → /api가 Supabase RLS 적용.  
2. 6단계 고정 순서가 아니라 agent가 필요한 정보만 묻고, 이전 진료 메모·사진 타임라인을 context로 참고.  
3. 사진 업로드 포함 입력 → 대본 카드 출력. 사진 날짜순 배치.  
4. Supabase에 암호화 저장(서버 평문 못 읽음, 평문 날짜·부위만 확인 가능).  
5. 기록 목록 왼쪽 사이드에서 열람, 이전 대본·사진 타임라인 불러오기 가능.

**공통**
- 응급 신호 입력 시 어느 단계에서든 119/즉시 병원 권장만 나오며, 이 판단은 매 턴 가장 먼저 수행되고 사용자 승인 없이 즉시 중단된다.
- tool 실패 상황(예: e약은요 0건, DUR 호출 실패 등)에서도 agent가 실패를 기록하고 대본은 진행하되, 실패한 항목은 대본에 별도 표시한다. 단, 응급 신호는 실패와 무관하게 우선 처리한다.
- Solar가 확신성 문장("이건 감기네요") 대신 권유 문장("감기로 의심되는데, 이비인후과를 가보는 게 어때요?")으로 출력한다.
- agent는 P0-2 허용 툴 6종 안에서만 동작하고, 세션당 툴 호출 최대 8회를 넘기면 더 확인하지 않고 현재 정보로 결과를 낸다.
- human 승인이 필요한 지점은 2개(질문 3개 확정 칩, 저장 전 동의 화면)로 제한되고, 데모에서 그 흐름이 보인다.

### 11) 제외 범위
- 의사 진단·처방 대행 아님.
- 복용 약 임의 중단·조정 조언 안 함.
- 법령·규정상 금지 콘텐츠(차별·혐오·폭력·음란·타인 명예훼손·타인 개인정보 무단 포함 등) 미포함.
- 카카오톡 전송은 이번 범위에서 제외(ver02 이후 재검토 가능 — 기존 ver01에서 보류한 것과 일관).
- 기기 간 키 공유 안 함(다른 기기에서 이전 기록 복호화 불가 — 원본 요청 "서버 못 읽게" 취지상 제약).
- 비회원 Supabase 저장 안 함(localStorage-only).
- 프론트(Vite+React)는 팀원 담당. 나는 PRD, /api, 진료과 규칙표, Supabase 테이블·RLS까지.
